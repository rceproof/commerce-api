주문·결제·포인트를 처리하는 백엔드 API 서버입니다.
웹 모의해킹 경력을 바탕으로 안전한 API 설계(SQL 인젝션 방어, 접근 통제)에 중점을 둡니다.

## 성능

### 주문 조회 인덱스 최적화

- **대상:** `GET /orders` — `user_id`로 본인 주문 조회
- **측정:** 주문 50만 건 기준 `EXPLAIN ANALYZE`
  - 인덱스 전: Seq Scan, 약 **8.9ms**
  - 인덱스 후(`orders_user_id_idx`): Bitmap Index Scan, 약 **0.11ms**
  - → 약 **79배** 단축
- 인덱스 정의는 `schema.sql`에 포함.

### N+1 조회 방지 설계

주문 목록에 상품명을 함께 보여줄 때, 주문마다 상품을 따로 조회하면 `1 + N`번의 쿼리(N+1 문제)가 발생한다. 이를 재현·비교해 설계를 검증했다. (`poc/n_plus_1_benchmark.js`)

- **측정:** 주문 78건을 가진 유저 기준

  | 방식                     | 쿼리 수 | 소요 시간 |
  | ------------------------ | ------- | --------- |
  | N+1 (주문마다 상품 조회) | 79번    | 24.3ms    |
  | JOIN (한 쿼리로 결합)    | 1번     | 0.9ms     |
  | 스냅샷 (현재 설계)       | 1번     | 0.7ms     |

- **선택: 스냅샷 설계** — 주문 생성 시 상품명을 `orders.product`에 저장해, 조회 시 상품 테이블을 보지 않는다.
- **이유:**
  - **성능** — 조회가 단일 쿼리로 끝나고 JOIN 비용조차 없음
  - **정확성** — 상품명·가격이 이후 변경돼도 주문은 **주문 당시의 값**을 그대로 보존 (주문 이력 왜곡 방지)
- **참고:** 위 수치는 앱·DB가 같은 로컬 환경 기준. 앱과 DB가 분리된 배포 환경에선 쿼리당 네트워크 왕복이 더해져 N+1과의 격차가 크게 벌어진다.

### 목록 페이지네이션

- `GET /orders`에 `page` / `limit` 쿼리 파라미터 지원 (기본 `page=1`, `limit=20`, `limit` 최대 100)
- `LIMIT` / `OFFSET`으로 페이지 단위 분할 → 응답 크기와 DB 부하를 낮춤
- 응답에 `total`, `totalPages` 메타데이터를 포함해 클라이언트 페이지 UI를 지원
- **참고(트레이드오프):** `OFFSET` 방식은 뒤쪽 페이지(높은 OFFSET)에서 건너뛸 행을 모두 읽어 성능이 저하됨. 트래픽 증가 시 keyset(커서) 방식으로 전환 가능.

### 부하 테스트 (k6)

`k6`로 가상 유저(VU)를 단계적으로 늘리며 처리량·지연을 측정했다. 스크립트는 `MAX_VUS`·`BASE_URL` 환경변수로 부하와 대상을 바꿀 수 있다. (`poc/load_orders.js`, `poc/load_products.js`)

- **측정:** 로컬, think-time 없이 연속 요청, 각 부하 수준까지 램프업

  | 대상                                         | 부하     | 처리량(RPS) | p95 지연 | 실패율 |
  | -------------------------------------------- | -------- | ----------- | -------- | ------ |
  | `GET /products` (단순 조회)                  | 100 VU   | ~5,000      | 17.8ms   | 0%     |
  | `GET /orders` (인증 + 페이지네이션, 50만 건) | 100 VU   | ~2,300      | 39ms     | 0%     |
  | `GET /orders`                                | 1,100 VU | ~2,300      | 468ms    | 0%     |
  | `GET /orders`                                | 1,150 VU | ~2,300      | 539ms    | 0%     |
  | `GET /orders`                                | 1,500 VU | ~2,300      | 662ms    | 0%     |

- **처리량 상한 ≈ 2,300 RPS:** VU를 100→1,500으로 15배 늘려도 처리량은 ~2,300 RPS로 일정하고 지연만 상승 — 전형적 포화 곡선.
- **SLO(p95<500ms) 한계 ≈ 1,100 VU:** 1,100 VU(468ms) 통과, 1,150 VU(539ms) 초과 (이분탐색으로 교차점 확인).
- **우아한 성능 저하:** 1,500 VU에서도 실패율 0% — 과부하에 터지지 않고 느려질 뿐(요청을 버리지 않고 대기 처리).
- **병목 분석 (가설 → 검증 → 재특정):** 처리량 상한을 DB 커넥션 풀(기본 10)로 가설 → 풀 50으로 A/B 측정(`pg_stat_activity`로 연결 50개 적용 확인)했으나 **처리량 변화 없음 → 풀은 병목 아님.** `top`으로 재확인: 시스템 CPU ~92% idle·DB도 한산한데 **단일 Node 프로세스가 CPU ~110%(코어 1개 포화)** → 병목은 **Node의 싱글 스레드 이벤트 루프**(한 프로세스가 1코어 이상 못 씀). 처리량 상향은 **수평 확장(Node cluster / 다중 인스턴스 + 로드밸런서)**이 정답.
- **DB 커넥션 풀 크기는 `DB_POOL_MAX` 환경변수로 조절 가능** (기본 10).
- **인덱스 유효성:** 50만 건을 2,300 RPS로 조회하며 포화 전 p95 39ms 유지 — `user_id` 인덱스가 부하에서도 유효.

## 보안 관리

### 의존성 취약점 패치 이력

- **2026-10-24** — `npm audit` 취약점 2건 패치
  - **body-parser** (High, GHSA-27r3-jxmh-p828): 압축 요청 본문 뒤 trailing bytes로 인한 DoS. `express.json()`이 gzip 본문을 해제하므로 실제 노출 경로가 존재해 우선 처리.
  - **ip-address** (Moderate, GHSA-rxp7-6hxx-x8q5): IPv6 파싱 2차 시간(ReDoS). 전이 의존성이며 앱에서 해당 파싱 경로를 사용하지 않아 위험은 낮으나 함께 상향.
  - 조치: `npm audit fix`(semver 호환) → 테스트 11건 통과 확인 → 재배포.

### 배포 이미지 하드닝

운영 배포(Docker)를 공격자 관점으로 점검해 **공격면과 노출 정보를 최소화**했다.

| 항목            | 조치                                            | 효과                                                              |
| --------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| API 문서 노출   | `NODE_ENV=production`에서 `/api-docs` 비활성화  | 운영에서 엔드포인트·파라미터·인증 방식 정보 노출 차단 (정찰 방어) |
| 불필요 코드     | `.dockerignore`에 `__tests__`, `poc`, 문서 제외 | 테스트·벤치 스크립트가 운영 이미지에 안 들어감                    |
| devDependencies | `npm ci --omit=dev`                             | jest·supertest 등 런타임에 불필요한 패키지 제외 (취약점 표면 ↓)   |
| 실행 권한       | `USER node` (root 대신 일반 유저)               | 컨테이너 내 RCE 시 권한 최소화 (CIS/K8s 기준)                     |
| 베이스 이미지   | `node:22` → `node:22-slim`                      | 이미지 약 1.1GB → **402MB**, OS 패키지 축소로 공격면 ↓            |

- **검증:** `docker compose up` 후 기동(`/` 200), 회원가입·로그인(bcrypt 정상), `/api-docs` **404**(비노출), 실행 유저 `node` 확인.
